# Guest Check-In Manager

Guest Check-In Manager is a production-quality sample application for recording
guest arrivals at restaurants, gyms, hotels, event venues, and similar
businesses. It provides a simple guest register, dashboard summaries, and
searchable daily records that can also support roll call during an emergency.

The application is designed as a single-tenant demonstration. Authentication,
authorization, users, organizations, and tenancy are intentionally out of
scope, but the service and repository boundaries leave room to add them later.

## Technology stack

- **Frontend:** Plain HTML, responsive CSS, and vanilla JavaScript
- **Backend:** Python and FastAPI
- **Database:** PostgreSQL
- **ORM:** SQLAlchemy 2.x
- **Migrations:** Alembic
- **API contract:** REST with automatically generated Swagger/OpenAPI docs
- **Containers:** Docker and Docker Compose
- **Static hosting:** Nginx
- **Tests:** pytest with a disposable PostgreSQL database

The frontend does not use React, Node.js, npm, a bundler, or a runtime build
step.

## Features

- Create a guest entry with a server-generated UTC check-in time.
- Automatically create exactly one daily register when the first guest checks
  in.
- View and filter a daily guest register by date.
- Search guest names case-insensitively.
- Sort newest check-ins first and navigate paginated results.
- View guest details and update notes or payment method.
- Keep guest name and check-in time immutable after creation.
- Delete guest entries without deleting the daily register.
- View today's count, the selected date's count, and the most common payment
  method on the dashboard.
- Display timestamps in the `Europe/London` timezone, with hours and minutes
  only.
- Provide loading, empty, success, and error states with accessible controls
  and a deletion confirmation step.

## Domain model

### `DailyGuestRegister`

Represents the register for one calendar date.

| Field | Description |
| --- | --- |
| `id` | UUID primary key |
| `register_date` | Unique date; one register per day |
| `created_at` | Timezone-aware UTC creation timestamp |

Users never create registers directly. Creating a guest entry for a date with
no register creates it automatically, safely handling concurrent requests.

### `GuestEntry`

Represents one guest check-in.

| Field | Description |
| --- | --- |
| `id` | UUID primary key |
| `register_id` | Foreign key to `DailyGuestRegister` |
| `guest_name` | Required, trimmed, non-blank, maximum 200 characters |
| `check_in_time` | Required, generated by the server, immutable |
| `notes` | Required on creation, trimmed, non-blank, maximum 2,000 characters |
| `payment_method` | Nullable on creation; updateable |
| `created_at` | Timezone-aware UTC creation timestamp |
| `updated_at` | Timezone-aware UTC update timestamp |

The API uses these payment method enum names:

`CASH`, `CARD`, `BANK_TRANSFER`, `MOBILE_PAYMENT`, `MEMBERSHIP`, `NONE`, and
`OTHER`.

`null` means that a payment method has not been recorded. `NONE` means that no
payment was required or made. `OTHER` means that a payment exists but does not
match another enum value. Human-readable labels belong to the frontend; API
enum values remain unchanged.

## API

The backend listens on port `8000` by default. Interactive documentation is
available at `/docs`, with the OpenAPI schema at `/openapi.json`.

### Endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Backend health check |
| `GET` | `/api/registers` | List daily registers |
| `GET` | `/api/registers/{date}` | Get one register by `YYYY-MM-DD` date |
| `GET` | `/api/guest-entries` | List paginated guest entries |
| `GET` | `/api/guest-entries/{id}` | Get one guest entry |
| `POST` | `/api/guest-entries` | Create an entry for the current UTC date |
| `PATCH` | `/api/guest-entries/{id}` | Update notes and/or payment method |
| `DELETE` | `/api/guest-entries/{id}` | Permanently delete an entry |
| `GET` | `/api/dashboard` | Get counts and payment-method summary |

`GET /api/guest-entries` supports:

- `date=YYYY-MM-DD`
- `search=guest name`
- `page` (default `1`)
- `page_size` (default `25`, maximum `100`)

Results include `items`, `page`, `page_size`, `total`, and `total_pages`.
Entries are sorted by check-in time descending, with deterministic ordering for
equal timestamps.

`GET /api/dashboard?date=YYYY-MM-DD` defaults to the current UTC date and
returns the selected date, today's guest count, the selected date's count, and
the most common non-null payment method. It returns `null` when no payment
method has been recorded. Ties use deterministic enum ordering.

### Request rules

On creation, clients submit only the guest name and notes, with an optional
payment method. Clients must not submit the register date, register ID, ID,
check-in time, or timestamps. The server always chooses the current application
date in UTC and generates `check_in_time`.

Updates can change only `notes` and `payment_method`. Empty patches, unknown
payment methods, blank text, overlong text, and attempts to change immutable or
server-managed fields are rejected with HTTP `422`.

Successful responses use HTTP `201` for creation, `200` for reads and updates,
and `204` with no body for deletion. Missing resources return `404`; applicable
conflicts return `409`. Errors use a consistent shape:

```json
{
  "detail": "Guest entry not found",
  "code": "GUEST_ENTRY_NOT_FOUND"
}
```

## Run with Docker Compose

### Prerequisites

- Docker Desktop with Docker Compose
- Git

### Start the application

```bash
docker compose up --build
```

Compose starts PostgreSQL, waits for its health check, runs
`alembic upgrade head` in the backend, and then starts FastAPI. PostgreSQL data
is stored in a persistent Docker volume, so restarting the stack does not
discard the database.

Open:

- Frontend: <http://localhost:3000>
- API documentation: <http://localhost:8000/docs>
- API health check: <http://localhost:8000/health>

Stop the stack while retaining data:

```bash
docker compose down
```

To remove the database volume and start with a fresh database, use the
project's named volume explicitly:

```bash
docker compose down -v
docker compose up --build
```

### Run migrations manually

For local backend development or troubleshooting:

```bash
cd backend
alembic upgrade head
```

The backend image uses `/app` as its working directory and sets
`PYTHONPATH=/app`, so the Alembic executable can import the `app` package.
Migrations use an async `postgresql+asyncpg` URL and import the SQLAlchemy
models before assigning Alembic's target metadata.

The initial migration creates the PostgreSQL `payment_method` enum exactly once
with `checkfirst=True`, creates tables and indexes in order, and is reversible.
It is safe both on a fresh database and after an interrupted startup. A second
`alembic upgrade head` after a successful migration is a no-op.

## Configuration

Keep secrets and local overrides in an uncommitted `.env` file. Typical
settings include:

```text
DATABASE_URL=postgresql+asyncpg://postgres:postgres@db:5432/guest_check_in
TEST_DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/guest_check_in_test
FRONTEND_ORIGIN=http://localhost:3000
```

The frontend reads the backend URL from a runtime configuration value such as
`window.APP_CONFIG.API_BASE_URL`. This keeps the API location configurable and
avoids hard-coding `http://localhost:8000` in application logic. Update the
frontend runtime configuration and the backend CORS origin together when
deploying to another host.

All database timestamps are timezone-aware UTC timestamps. API dates use
`YYYY-MM-DD`, API timestamps use ISO 8601 with timezone information, and the
frontend converts timestamps for display using `Europe/London`, including
daylight-saving changes.

## Testing

Tests use pytest and PostgreSQL rather than substituting SQLite for integration
coverage. Configure `TEST_DATABASE_URL` to point to a disposable test
database, then run:

```bash
pytest
```

The test suite should cover automatic and concurrent register creation,
one-register-per-day behavior, server-generated check-in times, rejection of
client-supplied server fields, immutable fields, nullable payment methods,
validation, pagination, date filtering, case-insensitive search, dashboard
aggregation and tie behavior, missing resources, updates, and deletion.

Before release, verify both:

1. A fresh database migrates successfully and the backend reaches `/health`.
2. A restart with the existing PostgreSQL volume succeeds, and the second
   `alembic upgrade head` performs no work.

# Guest Check-In Manager

Guest Check-In Manager is a production-quality demonstration for recording guest arrivals in restaurants, gyms, hotels, and event venues. It uses a FastAPI/SQLAlchemy backend, PostgreSQL persistence, Alembic migrations, and a mobile-first vanilla JavaScript frontend served by Nginx.

## Architecture

- `backend/app/models`: `DailyGuestRegister` and `GuestEntry` domain models.
- `backend/app/schemas`: Pydantic request and response validation.
- `backend/app/repositories`: database queries only.
- `backend/app/services`: register creation, entry mutations, pagination, and dashboard rules.
- `backend/app/api`: dependency-injected REST endpoints.
- `backend/alembic`: async PostgreSQL migration environment. The payment enum is created once with `checkfirst=True`.
- `frontend`: independent static HTML pages, CSS, and browser JavaScript. No Node.js or bundler is needed.

Authentication and tenancy are intentionally out of scope for this single-tenant demonstration. The service boundary leaves room to add them later without changing the domain model.

## Run with Docker Compose

Prerequisites: Docker Desktop with Compose v2.

```sh
docker compose up --build
```

The backend waits for PostgreSQL health, runs `alembic upgrade head`, and then starts FastAPI. The existing `postgres_data` volume is retained across restarts; rerunning the command makes the migration a no-op after the first successful migration.

- Frontend: <http://localhost:3000>
- API: <http://localhost:8000>
- Swagger UI: <http://localhost:8000/docs>
- Health: <http://localhost:8000/health>
- PostgreSQL: `localhost:5432` (`checkin` / `checkin`)

To stop containers while retaining data:

```sh
docker compose down
```

To remove the database volume and start fresh:

```sh
docker compose down -v
docker compose up --build
```

## Local backend development

Python 3.13 and PostgreSQL are required. From the repository root:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r backend\requirements.txt
$env:DATABASE_URL = "postgresql+asyncpg://checkin:checkin@localhost:5432/checkin"
cd backend
alembic upgrade head
uvicorn app.main:app --reload
```

The equivalent manual migration command is `alembic upgrade head` from `backend\`. Do not use `Base.metadata.create_all()`; schema changes are managed exclusively by Alembic.

The frontend can be served by any static web server. For a quick local check, serve `frontend\` on port 3000. Each HTML page defines `window.APP_CONFIG.API_BASE_URL`; change that value in the pages when the backend is hosted elsewhere. Docker Compose uses `http://localhost:8000`.

## API

- `GET /api/registers`
- `GET /api/registers/{date}`
- `GET /api/guest-entries?date=YYYY-MM-DD&search=name&page=1&page_size=25`
- `GET /api/guest-entries/{id}`
- `POST /api/guest-entries` with `{ "guest_name": "...", "notes": "..." }`
- `PATCH /api/guest-entries/{id}` with `notes` and/or nullable `payment_method`
- `DELETE /api/guest-entries/{id}`
- `GET /api/dashboard?date=YYYY-MM-DD`

Creation always uses the current UTC application date and server-generated UTC check-in timestamp. The frontend renders timestamps in `Europe/London` with daylight-saving support and no seconds. Null payment means “not recorded”; `NONE` means no payment was required or made. Dashboard payment ties are deterministic: SQL ordering uses descending count and then ascending enum name.

## Tests


SQLite is deliberately not supported for integration testing. A disposable PostgreSQL test database should be used for endpoint, concurrency, migration, and persistence coverage.
